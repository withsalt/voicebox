# Confucius4 优化 A/B 实测（2026-09-21）

本机实测支持两个结论：Mel 前端计算明显减少，完整离线识别有约 2.7% 的小幅收益；
实时推理的托管分配量减少约 19.5%，但**尚不能证明实时端到端延迟稳定下降**。
上一轮交付只完成了正确性检查和单侧实时试跑，不能据此声称性能提升。
这份记录补充了同机、同模型、相同输入的优化前后对照，保留了负面结果。

## 完整离线识别：预热后 A/B、B/A

每个进程先运行全部 6 条语音预热一轮，不计入结果；再测 5 轮，共 30 次识别。
第一组 baseline→candidate，第二组 candidate→baseline。以下为同步 `Decode` 累计耗时，
包括 Mel、encoder、tokenizer 和 decoder，不包括排队和模型加载。

| 运行顺序 | 基线 | 候选 | 耗时降低 | 配对文本差异 |
| --- | ---: | ---: | ---: | ---: |
| A→B，30 次 | 5.758972 s | 5.596694 s | 2.82% | 0/30 |
| B→A，30 次 | 5.728581 s | 5.584551 s | 2.51% | 0/30 |
| 合计，60 次 | 11.487554 s | 11.181245 s | 2.67% | 0/60 |

两组 CER 均为 0.9804%，没有变化。这里的 60 次来自 6 条语音重复，不能视为 60 条独立样本。
本轮离线托管分配分别减少 11.66% 和 10.51%；差异包含数组池/GC 的运行波动。

原始数据：`.perf/confucius4-ab/offline/round-{01,02}-{baseline,candidate}.json`。
对照结果：同目录 `comparison-01.json`、`comparison-02.json`。

## 实时：分配下降，延迟收益未确立

第一轮使用原 benchmark，只做服务默认的短音频预热，A→B，6 条语音各一次。
基线推理累计 8.956560 s，候选 9.432868 s，候选**慢 5.32%**；
推理次数两侧均为 185，配对文本无差异。不能把这个结果忽略或确定归因于噪声。

随后增加整套语音预热，反转为 B→A，每侧预热一轮、测两轮：

| 指标（12 次语句，370 次推理） | 基线 | 候选 | 变化 |
| --- | ---: | ---: | ---: |
| 推理累计时间 | 17.440421 s | 17.374710 s | 降低 0.38% |
| 推理 RTF | 0.288854 | 0.287766 | 降低 0.38% |
| 单次推理 P50 | 47.5790 ms | 47.2174 ms | 降低 0.76% |
| 单次推理 P95 | 62.2229 ms | 61.6988 ms | 降低 0.84% |
| Finish 排空时间中位数 | 34.2532 ms | 34.5218 ms | 增加 0.78% |
| Decode 线程托管分配 | 160,123,632 bytes | 128,874,920 bytes | 减少 19.52% |
| 配对文本差异 | — | 0/12 | 一致 |
| CER | 2.9412% | 2.9412% | 一致 |

P50/P95 由所有 370 个原始调用耗时合并后计算，不是各句 P95 的平均数。
分配量是 `GC.GetAllocatedBytesForCurrentThread` 的累计差值，不是 RAM/VRAM 占用，
也不包含 ORT native 内存、其他线程、送音和结果消费。
0.38% 的延迟差异与第一轮方向相反，不能作为稳定实时提速的证据。

原始数据：`.perf/confucius4-ab/{baseline,current}-realtime.json`（第一轮）、
`{baseline,candidate}-realtime-warm.json`（完整预热）。
汇总：`realtime-initial-comparison.json`、`realtime-warm-comparison.json`。

## CPU 前端组件

独立 `--mode frontend` 不加载 ONNX 图，只加载同一包的 Mel 配置。
每个操作预热至少 0.5 s，测 15 个批次，以下为每操作批次均值的中位数。
FFT 每批 4096 帧，完整 Mel 每批 8 次，流式 Mel 每批 4 个完整窗口。
统计不是单次更新的 P95。最终组件对照逐进程串行执行。

| 操作 | 基线 | 候选 | 耗时降低 |
| --- | ---: | ---: | ---: |
| 400 点 FFT，单帧 | 5.452 μs | 5.048 μs | 7.43% |
| 3.561 s 语音完整 Mel | 5.000 ms | 2.040 ms | 59.19% |
| 该语音全部增量 Mel 更新累计 | 5.560 ms | 2.617 ms | 52.93% |
| 6.211 s 语音完整 Mel | 8.170 ms | 3.559 ms | 56.44% |
| 该语音全部增量 Mel 更新累计 | 10.582 ms | 5.044 ms | 52.33% |

6 条样本完整 Mel 耗时降低范围为 55.82%～59.19%，增量窗口累计为 50.96%～53.53%。
不能把这约一半的 CPU 前端收益当作整段识别收益：以 6.211 s 语音为例，
所有流式更新累计仅节省约 5.54 ms，而整段 GPU 推理通常需要数秒累计计算。
FFT 原实现已有 SIMD Dot，因此运算次数减少也不等于按同倍数加速。

原始数据和汇总：`.perf/confucius4-ab/{baseline,candidate}-frontend.json`、`frontend-comparison.json`。

## 预热偏差与正确性范围

早期离线 6 条×2 次对比曾出现 10.96% 收益；6 条×5 次为 5.75%。
后者移除第一轮后仅 2.17%。这些初步结果保留在
`.perf/confucius4-ab/{baseline,current}-offline{,-r5}.json`，不作为最终稳态结论。

本次 C# 测试 24/24 通过，包括真实 FP16 CUDA 离线/流式 parity、Python Mel/提示词基线、
FFT vs 双精度直接 DFT 以及生命周期测试。评测统计新增 4 项 Python 单测通过。
对新增测试代码完成代码审查，重点检查预热排除、配对校验、百分位、计时和分配范围。

FFT 改写改变了浮点运算顺序，数值上不是逐位相等；已有误差容限测试及这些语音转写一致，
但本次仅覆盖 6 条中文性能样本与现有 parity 音频，未重新完成 189 条中文/73 条英文全量验收。
没有修改导出模型，因此这里没有模型导出优化的提速结论。CPU/ARM、其他 GPU、噪声语音、
长窗、多会话、其他语言需要独立验证，不能从这些数据推断普遍无退化。
